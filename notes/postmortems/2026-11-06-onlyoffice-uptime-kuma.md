# Monitoring: ONLYOFFICE Docs в Uptime Kuma

- **Parent document:** [`2026-11-06-onlyoffice-clone-vm-and-rabbitmq.md`](./2026-11-06-onlyoffice-clone-vm-and-rabbitmq.md)
- **Related:** [`2026-11-06-onlyoffice-jwt-enablement.md`](./2026-11-06-onlyoffice-jwt-enablement.md)
- **Статус:** Applied
- **Компонент:** Uptime Kuma → ONLYOFFICE Docs (healthcheck)
- **Среда:** домашняя лаборатория, Hyper-V, Ubuntu Server 24.04, Docker, Uptime Kuma 1.23.16

## 1. Контекст

После инцидента 2026-11 (отказ ONLYOFFICE из-за повреждённой базы RabbitMQ) сервис был восстановлен и защищён JWT. Следующий шаг - сделать так, чтобы подобный отказ **обнаруживался автоматически**, а не при попытке открыть документ.

В домашней лаборатории уже работает **Uptime Kuma** - self-hosted монитор, который отслеживает 13 сервисов (DokuWiki, NPM, Nextcloud, Vaultwarden, Dashy, SnipeIT и др.). На момент инцидента ONLYOFFICE в этом списке **отсутствовал** - поэтому отказ заметил пользователь, а не система. Добавление ONLYOFFICE в мониторинг закрывает этот разрыв.

## 2. Тип монитора: `HTTP(s) - Keyword` («HTTP(s) - Слово»)

В Uptime Kuma 1.23.16 доступен тип `HTTP(s) - Keyword` (в русской локализации - **«HTTP(s) - Слово»**). Используется именно он, потому что проверяет **тело ответа** на наличие `true`, а не только код `200`.

- **Почему не обычный `HTTP(s)`:** эндпоинт `/healthcheck` возвращает `200 OK` с телом `true`. Теоретически сервис может отвечать `200` с телом `false` (частичная деградация) - обычный HTTP-монитор покажет «всё хорошо», хотя приложение не работает. `Keyword` ловит оба сценария: и обрыв/таймаут, и `200 + false`.

Для остальных сервисов домашней лаборатории (DokuWiki, NPM, Dashy, Vaultwarden и др.) достаточно обычного `HTTP(s)` - у них нет healthcheck-эндпоинта с осмысленным телом.

## 3. Настройка монитора

В Uptime Kuma → **+ Add New Monitor**:

| Поле | Значение |
|---|---|
| Тип монитора / Monitor Type | `HTTP(s) - Слово` / `HTTP(s) - Keyword` |
| Имя / Friendly Name | `ONLYOFFICE Docs` |
| URL | `https://<OFFICE_SUBDOMAIN>.<DOMAIN>/healthcheck` |
| Слово / Keyword | `true` |
| Частота опроса / Heartbeat Interval | `600` |
| Попыток / Retries | `2` |
| Интервал повтора / Retry Interval | `600` |
| Тайм-Аут запроса / Request Timeout | `48` |
| Макс. перенаправлений / Max Redirects | `0` |
| Допустимые коды / Accepted Status Codes | `200-299` (по умолчанию) |

- **Про интервалы 600 / 600.** Это **осознанный выбор** для self-hosted homelab: приоритет - минимум шума и уведомлений, а не секундное обнаружение. **Следствие:** при реальном падении обнаружение занимает до ~30 минут (2 retry × 600 сек + первичная проверка). Для production-контура оба интервала были бы 60–120 сек. Если сервис станет критичнее - уменьшить.

- **Про `Retries: 2`.** Дефолт в Uptime Kuma - `0`, при котором **любой** единичный сбой сразу помечает сервис как DOWN. Это даёт ложные тревоги при кратковременных перезапусках контейнера. `2` retry сглаживает единичные сбои.

- **Про `Request Timeout: 48`.** Оставлено дефолтное значение. Healthcheck отвечает мгновенно, но 48 сек даёт запас на случай сетевых задержек Hyper-V. Уменьшать до 30 не стали: разница несущественна, а запас полезен.

- **Про `Max Redirects: 0`.** Healthcheck не редиректит. Если NPM вдруг начнёт отдавать 301/302, монитор увидит это сразу, а не «провалится сквозь» редирект.

После сохранения монитор появляется в общем списке и начинает проверять сервис **раз в 10 минут**. Статус должен стать зелёным (100%) в течение 2–3 минут (первая проверка при сохранении).

## 4. Проверка эндпоинта вручную

Перед добавлением монитора полезно убедиться, что эндпоинт отвечает:

```bash
curl -s https://<OFFICE_SUBDOMAIN>.<DOMAIN>/healthcheck
# ожидаемо: true
```

Если `true` - монитор будет работать. Если пусто, ошибка или `false` - сначала разобраться с сервисом, потом добавлять монитор.

> **Важно: URL должен содержать `/healthcheck`.** Голый `https://<OFFICE_SUBDOMAIN>.<DOMAIN>/` отдаёт `308`-редирект на `/welcome/`, а не `true`. Если в URL монитора нет `/healthcheck`, keyword-монитор будет искать `true` в HTML welcome-страницы и **всегда показывать DOWN**. Это самая частая ошибка при настройке.

## 5. Status Page

Монитор добавлен на существующую Status Page (`https://<STATUS_SUBDOMAIN>.<DOMAIN>/status/<STATUS_SLUG>`). В Uptime Kuma → **Status Pages** → ваша страница → **Edit** → **Monitors** → отметить галочкой `ONLYOFFICE Docs` → **Save**.

После этого `ONLYOFFICE Docs` отображается в публичном списке рядом с остальными сервисами (DokuWiki, NPM, Nextcloud, Vaultwarden и т. д.).

## 6. Что это даёт

- **Раннее обнаружение обрыва/таймаута.** Если сервис снова «зависнет» на RabbitMQ, монитор перехватит обрыв соединения и переключится в DOWN. С учётом интервалов 600/600 - в течение ~10–30 минут (первая проверка + 2 retry). Для homelab приемлемо; для production - уменьшить интервалы.
- **Ловит частичную деградацию.** В отличие от обычного `HTTP(s)`, keyword-монитор увидит `200 OK` с телом `false` и тоже уйдёт в DOWN.
- **Историчность.** Uptime Kuma хранит heartbeat-бары. По ним видно, **когда** были падения и **как долго** сервис был недоступен. Это полезно при разборе следующего инцидента: не нужно гадать, «когда это началось».
- **Единая панель.** Все сервисы домашней лаборатории в одном месте. Если падает несколько одновременно (например, Nextcloud и Mistworld - оба сейчас показывают ~80.8%), это сигнал о проблеме на уровне хоста/сети, а не конкретного сервиса.

## 7. Уведомления

Монитор без уведомлений полезен только если вы регулярно смотрите в панель. Для домашней лаборатории минимально достаточный канал - **Telegram-бот** (5 минут настройки через `@BotFather`). Настроить: **Settings → Notifications → Setup Notification → Telegram**.

После настройки Uptime Kuma присылает сообщение, когда монитор переходит в DOWN и когда возвращается в UP. Это ровно то, что превращает мониторинг из «красивой панели» в рабочий инструмент.

## 8. Чек-лист добавления в мониторинг

- [ ] `curl -s https://<OFFICE_SUBDOMAIN>.<DOMAIN>/healthcheck` → `true`
- [ ] В Uptime Kuma создан монитор типа `HTTP(s) - Слово` / `HTTP(s) - Keyword`
- [ ] URL - с полным путём `/healthcheck` (не голый домен)
- [ ] Keyword - `true`
- [ ] Интервалы 600/600, retries 2, timeout 48, max redirects 0 (осознанный выбор для homelab)
- [ ] Монитор показывает зелёный статус через несколько минут
- [ ] Монитор добавлен на Status Page
- [ ] Настроен хотя бы один канал уведомлений
- [ ] (Опционально) Второй монитор: Nextcloud → `https://<DOMAIN>/status.php`, ожидание JSON с `"installed": true` - честнее, чем проверка главной страницы
