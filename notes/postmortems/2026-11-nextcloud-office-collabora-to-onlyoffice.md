# Postmortem: Nextcloud Office - замена Collabora на ONLYOFFICE

- **Статус:** Resolved
- **Компонент:** Nextcloud Office / Collabora Online → ONLYOFFICE Docs
- **Среда:** домашняя лаборатория, Hyper-V, Ubuntu Server 24.04, Nextcloud, Nginx Proxy Manager
- **Характер:** постмортем по реальному инциденту, без поиска виноватых
- **Публикация:** все домены, IP, имена ВМ и учётные записи заменены на плейсхолдеры.

---

## 1. Summary

В работающем Nextcloud перестал нормально функционировать онлайн-офис на базе Collabora / Nextcloud Office. Сам Nextcloud оставался стабильным: файлы, календарь, чат, почта и магазин приложений работали. Проблема была локальной, но критичной: офисные документы не открывались или открывались с ошибками, а ключевые функции редактора - копирование и вставка через браузер - перестали работать.

Стандартные методы лечения не дали устойчивого результата: перезапуск snap, перезагрузка ВМ, переустановка приложений, увеличение RAM/CPU и проверка HTTPS напрямую без прокси. Диагноз: установленная связка Collabora / Nextcloud Office оказалась нестабильной в данной среде.

**Итоговое решение:** полностью отказаться от Collabora и развернуть ONLYOFFICE Docs через Docker на отдельном внутреннем порту, с публикацией через Nginx Proxy Manager по отдельному поддомену. После миграции онлайн-офис заработал полностью, включая копирование-вставку и совместимость с `.docx`.

---

## 2. Impact

- Онлайн-офис в Nextcloud был недоступен или частично неработоспособен.
- Документы открывались с ошибкой «Сервер был отключен» либо зависали на загрузке.
- При частичном открытии не работали базовые функции: копирование и вставка текста из буфера обмена.
- Терялись элементы форматирования, например цвет текста.
- Остальные сервисы Nextcloud работали штатно, поэтому проблема не была похожа на отказ всего сервера.

Для домашней лаборатории это был критичный функциональный сбой: онлайн-офис был нужен как замена настольному пакету и как часть сценария «своё облако».

---

## 3. Trigger

Точная причинно-следственная связь не была доказана экспериментально. Инцидент проявился после серии изменений конфигурации виртуальной машины `<VM_NAME>`: изменения ресурсов CPU/RAM.

Нельзя утверждать, что именно изменение ресурсов «сломало» Collabora. Более корректная формулировка: **после изменения ресурсов проявился устойчивый дефект, который не устранялся перезапусками и переустановкой.**

---

## 4. Detection

Проблема была обнаружена пользователем при попытке открыть офисный документ в Nextcloud. Симптомы:

- ошибка «Сервер был отключен»;
- зависание на этапе загрузки документа;
- документ иногда открывался, но копирование и вставка не работали;
- пропадали элементы форматирования;
- `sudo snap restart nextcloud` давал лишь временный эффект или не помогал;
- `sudo reboot` восстанавливал «двигатель» Collabora, но не решал проблему с копированием-вставкой.

---

## 5. Timeline

**T0. Исходное состояние**
Nextcloud работал на Ubuntu Server 24.04 в Hyper-V. Онлайн-офис был установлен через магазин приложений Nextcloud:
- Nextcloud Office;
- Collabora Online - Built-in CODE Server.

Nextcloud был доступен по HTTPS через Nginx Proxy Manager. SSL-сертификат работал. Остальные приложения Nextcloud функционировали.

**T1. Изменение ресурсов ВМ**
Были изменены ресурсы виртуальной машины `<VM_NAME>`: CPU/RAM. После этого онлайн-офис начал сбоить.

**T2. Первичные попытки лечения**
Были выполнены:
- перезапуск служб Nextcloud;
- полная перезагрузка ВМ;
- удаление и повторная установка Nextcloud Office и Collabora Online - Built-in CODE Server;
- увеличение RAM до 4 ГБ и CPU до 6;
- временное отключение Nginx Proxy Manager и получение SSL напрямую на Nextcloud.

Это доказало, что проблема не в сети, не в DNS, не в прокси и не в SSL. Проблема была в самом приложении Collabora / связке с Nextcloud Office.

**T3. Диагноз**
Установленная версия Collabora либо сам snap-пакет, либо связка с Nextcloud Office оказалась нестабильной в данной среде. Дальнейшее «лечение» было признано бесперспективным.

**T4. Стратегическое решение**
Полностью отказаться от Collabora и заменить его на ONLYOFFICE Docs. Для максимального контроля выбрана установка через Docker, а не через snap или приложение из магазина.

**T5. Зачистка**
Внутри Nextcloud через SSH были удалены связанные приложения:

```bash
sudo nextcloud.occ app:remove onlyoffice
sudo nextcloud.occ app:remove nextcloud_office
sudo nextcloud.occ app:remove richdocumentscode
```

На уровне ОС проверены возможные «контейнеры-призраки»:

```bash
sudo docker ps -a
```

Если находился контейнер Collabora:

```bash
sudo docker stop <collabora_container_name>
sudo docker rm <collabora_container_name>
```

**T6. Установка ONLYOFFICE Docs через Docker**
На ВМ `<VM_NAME>` был запущен официальный контейнер ONLYOFFICE Docs:

```bash
sudo docker run -i -t -d -p 8888:80 --restart=always \
  -e JWT_ENABLED=false onlyoffice/documentserver
```

Ключевые моменты:
- `-p 8888:80` — сервис опубликован на внутреннем порту 8888, чтобы не конфликтовать с Nextcloud и другими сервисами;
- `--restart=always` — контейнер поднимается после перезагрузки;
- `-e JWT_ENABLED=false` — JWT отключён для упрощения настройки **в домашней лаборатории**;
- `onlyoffice/documentserver` — образ **без тега** (то есть `latest`). Так было выполнено на момент инцидента.

> **Важно:** `JWT_ENABLED=false` допустим только в изолированной лаборатории. Для публичного сервера нужно включить JWT и настроить секрет в коннекторе Nextcloud.

> **Историческая точность.** На момент этого инцидента образ тянулся **без тега** (`latest`). Версия контейнера, созданного здесь, **неизвестна**: он был удалён годом позже при другом инциденте (см. [`2026-11-06-onlyoffice-clone-vm-and-rabbitmq.md`](./2026-11-06-onlyoffice-clone-vm-and-rabbitmq.md), раздел 5 / T7, и [`2026-11-06-onlyoffice-clone-vm-and-rabbitmq.evidence.md`](./2026-11-06-onlyoffice-clone-vm-and-rabbitmq.evidence.md), A.6). Урок «фиксировать версию» появился **после** второго инцидента. Финальная рекомендованная форма — с тегом (`onlyoffice/documentserver:<version>`) — приведена в постмортеме #2, раздел 8 (Resolution). Смешивать историческую и рекомендованную формы в одном разделе нельзя: читатель должен видеть, **что делали тогда**, и отдельно — **что делать сейчас**.

**T7. Настройка Nginx Proxy Manager**
На DNS-провайдере была создана A-запись для поддомена:

```text
<OFFICE_SUBDOMAIN>.<DOMAIN> → <PUBLIC_IP>
```

В Nginx Proxy Manager создан новый proxy host:

```text
Domain Name: <OFFICE_SUBDOMAIN>.<DOMAIN>
Scheme: http
Forward Hostname / IP: <INTERNAL_IP>
Forward Port: 8888
Websockets Support: enabled
```

На вкладке SSL:
- получен сертификат Let’s Encrypt;
- включён Force SSL.

**Websockets обязательны:** без них ONLYOFFICE может открывать документы, но совместное редактирование и часть интерактивных функций будут нестабильны.

**T8. Установка и настройка коннектора**
В Nextcloud через магазин приложений установлен коннектор ONLYOFFICE. В настройках:

```text
Администрирование → ONLYOFFICE
Адрес ONLYOFFICE Docs: https://<OFFICE_SUBDOMAIN>.<DOMAIN>
Секретный ключ: пусто, если JWT отключён
```

Если JWT включён, секрет должен совпадать с `JWT_SECRET` контейнера ONLYOFFICE.

**T9. Проверка**
После настройки создание и открытие `.docx` заработало. Копирование и вставка через браузер заработали «из коробки». Форматирование перестало пропадать.

**T10. Резервная копия**
Сразу после успешной миграции была создана новая чистая резервная копия / экспорт всей ВМ `<VM_NAME>`.

---

## 6. Root Cause

Точный root cause на уровне исходного кода не устанавливался. По совокупности признаков:

- проблема не была сетевой;
- проблема не была связана с NPM;
- проблема не была связана с SSL;
- проблема не была связана с нехваткой ресурсов;
- проблема воспроизводилась после чистой переустановки приложений;
- проблема сохранялась при прямом HTTPS без прокси.

Наиболее вероятная причина: нестабильность установленной версии Collabora / Nextcloud Office или внутренний баг связки snap-пакета с Nextcloud. Формулировка **«нестабильная в данной среде версия»** точнее, чем «Collabora плохой»: в других версиях и конфигурациях Collabora может работать нормально.

**Open question.** В отдельном изолированном контуре (air-gapped, другой сервер) та же связка Collabora / Nextcloud Office работала без сбоев. Это ослабляет гипотезу «фундаментально нестабильная версия» и указывает на то, что триггер мог быть связан со средой: изменение ресурсов на живой ВМ Hyper-V, состояние снапшота, взаимодействие с NPM. Точная причинно-следственная связь не установлена. Для production-контура это означало бы необходимость воспроизведения на чистой ВМ перед изменением ресурсов.

## 7. What Didn’t Work

| Действие | Результат |
|---|---|
| `sudo snap restart nextcloud` | Временный эффект или отсутствие эффекта |
| `sudo reboot` | Восстанавливал Collabora, но не решал проблему копирования-вставки |
| Удаление и чистая переустановка Nextcloud Office и Collabora Online | Не устранило баг |
| Увеличение RAM до 4 ГБ и CPU до 6 | Не решило проблему |
| Отключение NPM и прямой HTTPS на Nextcloud | Доказало, что проблема не в прокси и не в SSL |

---

## 8. Resolution

Рабочее решение:

1. Удалить Nextcloud Office, Collabora Online — Built-in CODE Server и связанные остатки.
2. Проверить и удалить старые Docker-контейнеры Collabora, если они были.
3. Запустить ONLYOFFICE Docs в Docker на внутреннем порту 8888.
4. Создать отдельный поддомен `<OFFICE_SUBDOMAIN>.<DOMAIN>`.
5. Настроить Nginx Proxy Manager: `http → <INTERNAL_IP>:8888`, включить Websockets, Let’s Encrypt, Force SSL.
6. Установить коннектор ONLYOFFICE в Nextcloud.
7. Указать адрес `https://<OFFICE_SUBDOMAIN>.<DOMAIN>`.
8. Проверить создание, открытие, копирование-вставку и форматирование `.docx`.
9. Сделать экспорт/резервную копию ВМ.

> **Примечание.** Все шаги в этом разделе приведены **в том виде, в каком они выполнялись** на момент инцидента. Образ запускался **без тега** (`latest`); версия контейнера неизвестна — он удалён годом позже при другом инциденте (см. [постмортем #2](./2026-11-06-onlyoffice-clone-vm-and-rabbitmq.md), раздел 5 / T7, и [evidence](./2026-11-06-onlyoffice-clone-vm-and-rabbitmq.evidence.md), A.6). Финальная рекомендованная форма (с зафиксированной версией `onlyoffice/documentserver:<version>`) — в постмортеме #2, раздел 8 (Resolution). Причина разделения: хронологически этот инцидент — раньше, и в тот момент правило «фиксировать тег» ещё не было выработано.

## 9. Result

После миграции:

- онлайн-офис заработал полностью;
- копирование и вставка через браузер заработали;
- форматирование перестало теряться;
- `.docx` открывается корректно;
- ONLYOFFICE лучше подошёл для документов Microsoft Office, чем Collabora в этой конфигурации;
- Nextcloud остался стабильным;
- появился отдельный управляемый вход через NPM и отдельный SSL-сертификат.

## 10. Lessons Learned

- **Не стоит бесконечно «лечить» нестабильный инструмент.** Если перезапуски, переустановки, ресурсы и проверка сети не помогают - стратегическая замена может быть быстрее и надёжнее.
- **Docker даёт больше контроля и предсказуемости,** чем «чёрные ящики» вроде snap или нестабильных приложений из магазина. Версию контейнера можно зафиксировать, логи и порты - контролировать.
- **Docker даёт контроль только при фиксации версии.** `onlyoffice/documentserver:<version>` предсказуемее, чем `latest`: при перезапуске не приедет другая версия.
- **Разделение ответственности через NPM удобно.** Nextcloud, ONLYOFFICE, почта и другие сервисы могут жить на разных внутренних портах, а публиковаться через отдельные поддомены.
- **Websockets обязательны для ONLYOFFICE.** Без них часть функций будет нестабильна.
- **JWT лучше не отключать на публичном сервере.** В домашней лаборатории `JWT_ENABLED=false` упрощает старт, но для публикации нужно включать JWT и хранить секрет в менеджере секретов.
- **Перед изменениями ресурсов ВМ нужна контрольная точка Hyper-V.** Это не было сделано вовремя, что усложнило диагностику.
- **Резервная копия после успешной миграции - обязательна.** Экспорт ВМ после победы фиксирует рабочее состояние.

---

## 11. Prevention

- Делать checkpoint Hyper-V перед изменением CPU/RAM, обновлением и установкой крупных приложений.
- Для ONLYOFFICE использовать Docker с **зафиксированной версией образа**, а не `latest`.
- Публиковать ONLYOFFICE через NPM с Websockets и Let’s Encrypt.
- Включить JWT для публичного доступа.
- Хранить пароли и секреты в менеджере секретов, не публиковать их в GitHub/DokuWiki.
- Вести журнал изменений: что менялось, когда, зачем.
- После успешной настройки делать экспорт ВМ и проверять восстановление.

## 12. Appendix: команды миграции

```bash
# Удаление старых приложений Nextcloud
sudo nextcloud.occ app:remove onlyoffice
sudo nextcloud.occ app:remove nextcloud_office
sudo nextcloud.occ app:remove richdocumentscode

# Проверка старых Docker-контейнеров
sudo docker ps -a

# Если найден старый контейнер Collabora
sudo docker stop <collabora_container_name>
sudo docker rm <collabora_container_name>

# Запуск ONLYOFFICE Docs (версия зафиксирована)
sudo docker run -i -t -d -p 8888:80 --restart=always \
  -e JWT_ENABLED=false onlyoffice/documentserver:<version>

# Проверка, что контейнер работает
sudo docker ps
```

**NPM:**

```text
Domain: <OFFICE_SUBDOMAIN>.<DOMAIN>
Scheme: http
Forward IP: <INTERNAL_IP>
Forward Port: 8888
Websockets Support: ON
SSL: Let's Encrypt + Force SSL
```

**Nextcloud:**

```text
Администрирование → ONLYOFFICE
Адрес ONLYOFFICE Docs: https://<OFFICE_SUBDOMAIN>.<DOMAIN>
Секретный ключ: пусто при JWT_ENABLED=false
```

> **Сноска (не для домашнего контура):** если ONLYOFFICE 7.5+ не может скачать документ по приватному IP и в логах появляется `DNS lookup ... is not allowed. Because, It is private IP address`, в изолированных средах добавляют `-e ALLOW_PRIVATE_IP_ADDRESS=true`. В домашнем контуре с NPM и публичным поддоменом это не требуется.
