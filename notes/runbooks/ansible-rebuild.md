# Runbook: Ansible-восстановление homelab

## Контекст

Плейбук `deploy_homelab.yml` разворачивает **минимальный воспроизводимый контур** на одном хосте: базовый харденинг ОС (UFW, Fail2ban, синхронизация времени) и запуск стека через `docker compose up -d`.

Это **не** описание всей self-hosted инфраструктуры. Реальная лаборатория шире - несколько ВМ, роли (`common`, `docker`, `apache`, `mumble`), разные пользователи на разных хостах. В публичный репозиторий она **не переносится** (OPSEC: реальные IP, домены, учётные записи). Здесь - **минимальный контур**, который можно запустить на чистой ВМ и проверить, что процесс работает. Ролевая структура реальной инфраструктуры описана в приватной DokuWiki; рефакторинг публичного плейбука под роли - отдельная задача (см. «Куда расти»).

## Предусловия

- **Ansible** установлен на control-node.
- **SSH-ключ** с control-node до целевого хоста (без пароля). Если ключа нет - `ssh-keygen` + `ssh-copy-id`.
- **Docker и Docker Compose** уже установлены на целевом хосте. Плейбук их **не ставит** - это предусловие, а не шаг.
- **Inventory-файл** создан из шаблона: `cp ansible/inventory/hosts.example ansible/inventory/hosts`, заменён IP и пользователь.
- **`deploy_dir`** (по умолчанию `/home/<user>/homelab`) содержит `docker-compose.yml` того стека, который нужно поднять. Плейбук только запускает `docker compose up -d` в этой директории; сами сервисы он не создаёт.

## Структура проекта

```
ansible/
├── ansible.cfg                    # конфиг: inventory, callback, host_key_checking
├── inventory/
│   └── hosts.example              # шаблон адресной книги (IP, user, ключ)
└── playbooks/
    └── deploy_homelab.yml         # плейбук: харденинг + docker compose up
```

## Запуск

1. **Проверка связи** со всеми хостами из inventory:
   ```bash
   ansible -i inventory/hosts all -m ping
   ```
   Ожидаемо: `SUCCESS => {"ping": "pong"}` для каждого хоста. Если `UNREACHABLE` - проверить SSH-ключ и IP.

2. **Dry-run** (без изменений на хосте):
   ```bash
   ansible-playbook playbooks/deploy_homelab.yml --check --diff
   ```
   Показывает, что **будет** изменено. На чистой ВМ увидите задачи, которые «would change»; на уже настроенной - `ok`.

3. **Боевой запуск:**
   ```bash
   ansible-playbook playbooks/deploy_homelab.yml
   ```
   Ожидаемо: `PLAY RECAP` с `changed=N`, `failed=0`. Если `failed` - смотреть задачу, на которой упало (обычно это отсутствие Docker или неверный `deploy_dir`).

## Проверка

После успешного запуска:

```bash
# Firewall: default deny incoming, открыты только 22/80/443/81
sudo ufw status verbose

# Fail2ban: active (running)
systemctl status fail2ban --no-pager

# Контейнеры стека: Up
docker ps

# Синхронизация времени: System clock synchronized: yes
timedatectl status
```

Если `ufw status` показывает `Status: inactive` - плейбук не включил UFW (проверить, был ли `become: true` и права). Если `docker ps` пуст - `docker compose up -d` не нашёл `docker-compose.yml` в `deploy_dir`.

## Известные ограничения

- **Docker не устанавливается плейбуком.** Предусловие: Docker и Compose уже на хосте. Если нужно ставить - добавить задачу с официальным репозиторием (отдельная работа).
- **NPM не настраивается.** Плейбук только открывает порт `81` для bootstrap-панели. Создание proxy-host'ов, SSL и доменов - вручную, после запуска.
- **`changed_when` может не отметить первый запуск как changed.** Условие `'Started' in stdout or 'Running' in stdout` не срабатывает, если контейнеры создаются впервые (в выводе `Created`). Это **косметика статуса**, не ошибка запуска. Исправление - `changed_when: compose_output.rc == 0` (отдельная правка).
- **Стек не описан.** Плейбук делает `docker compose up -d` в `deploy_dir`, но **что** за стек - зависит от `docker-compose.yml`, который лежит там. Плейбук не создаёт и не валидирует compose-файл.

## Куда расти

В реальной инфраструктуре плейбук разбит на **роли**:

- `common` - базовый набор для всех хостов (пакеты, timezone, NTP);
- `docker` - установка Docker;
- `apache` - веб-сервер;
- `mumble` - конкретный сервис.

Это позволяет применять разные наборы к разным группам хостов (`docker_vm`, `web_vms`) и переиспользовать роли между проектами. В публичном репозитории сейчас **плоский плейбук** для одного хоста - проще для минимального контура. Рефакторинг в роли - отдельная задача, не блокирует текущее использование.

## Философия

Ansible - это не «ещё один инструмент для выполнения команд», а **смена подхода**: от ручного администрирования (`ssh`, `apt install`, `nano`) к **инфраструктуре как коду**. Серверы - «оркестр», Ansible - «дирижёр», плейбук - «партитура».

Ключевой принцип - **идемпотентность**. Ansible не «выполняет» команду, а **приводит систему в нужное состояние**. Если пакет уже установлен - `ok`; если нет - `changed`. Повторный запуск плейбука на настроенной системе - это не «переустановка», а **аудит** соответствия «чертежу». Отсюда и ценность: плейбук - это не разовый скрипт, а **живая документация** инфраструктуры, которую можно запускать сколько угодно раз и получать один и тот же результат.
